# Workflow Web UI 用户旅程

> 从发现 workflow → 启动 → 观察 → 控制 → 完成，完整生命周期。
> 日期：2026-07-08

---

## 旅程概览

```
发现 workflow → 表达需求 → 确认参数 → 启动 → 观察运行 → 处理异常 → 完成 → 查看结果
    S0            S1          S2         S3       S4          S5         S6       S7
   浏览清单      描述需求     确认 args   发送指令   双通道监控   干预控制    收到通知   归档/重跑
```

## S1：表达需求 — "我想跑某个 workflow，需求是…"

### 场景 A：直接说需求（自然语言）

用户看过 workflow 列表后，在聊天窗口输入：

```
用户: 帮我跑 sprint-serial，两个任务：
  1. 实现用户登录 API，测试用 npm test -- task-1
  2. 实现订单管理 API，测试用 npm test -- task-2
  最多重试 3 次
```

### 场景 B：点击模板按钮

用户点击聊天窗口的 `[📋 使用此模板]` 或底部的 `[💡 模板 ▼]` → 选择 `sprint-serial`：

```
┌────────────────────────────────────────────┐
│ 📋 sprint-serial 参数编辑                   │
├────────────────────────────────────────────┤
│                                            │
│ 任务列表:                                  │

│ │     │ 实现用户登录 API            │     │ │
│ │     └────────────────────────────┘     │ │
│ │     Test Cmd: [npm test -- task-1]     │ │

│ │ [2] 任务名称: [task-2           ]      │ │
│ │     Dev Prompt:                        │ │
```

### 用户可能遇到的问题

| 问题 | 用户心理 | 系统如何帮助 |
|------|---------|-------------|
| "testCmd 写什么格式？" | 不确定测试命令写法 | 提供示例占位符 |
| "devPrompt 要写多详细？" | 不知道 agent 能理解多少 | 提示："写得越具体，agent 做得越准" |
| "我想加第 3 个任务" | 模板默认只有 2 个 | 点击 [+ 添加任务] 动态添加 |
| "我想换模型跑" | 觉得 sonnet 不够强 | 弹窗底部可切换模型 |

## S2：确认参数 — "AI 理解对我的意思了吗？"

用户发送后，系统不立即启动，而是先确认解析结果：

```

│ 🤖 好的，我来启动 sprint-serial，        │
│    参数如下，确认后开始执行：             │
│                                          │
│ ┌─ 参数确认 ─────────────────────────┐   │
│ │                                    │   │
│ │ Workflow: sprint-serial            │   │
│ │ 环境: JEREH Proxy                  │   │
│ │ 模型: qwen3.6-sonnet               │   │
│ │                                    │   │
│ │ 任务 1: task-1                     │   │
│ │   Dev: 实现用户登录 API             │   │
│ │   Test: npm test -- task-1        │   │
│ │                                    │   │
│ │ 任务 2: task-2                     │   │
│ │   Dev: 实现订单管理 API             │   │

│ │                                    │   │
│ │ 最大重试: 3 次                      │   │
│ │                                    │   │
│ │ [✏️ 修改参数]    [🚀 确认启动]      │   │
│ └────────────────────────────────────┘   │
└──────────────────────────────────────────┘
```

### 用户可能遇到的问题

| 问题 | 用户心理 | 系统如何帮助 |
|------|---------|-------------|
| "testCmd 解析错了" | AI 没正确提取命令 | 点 `[✏️ 修改参数]` 弹出编辑框直接改 |
| "环境选错了" | 底部选的是 ANTHROPIC 但想用 JEREH | 确认框底部可切换环境 |
| "对了，我想加个 task-3" | 突然想起漏了任务 | 点 `[✏️ 修改参数]` 添加任务后再发 |

### 用户操作

- **[🚀 确认启动]** → 进入 S3
- **[✏️ 修改参数]** → 弹回参数编辑框，改完再确认
- **直接在聊天窗口回复** → "不对，task-1 的 testCmd 应该是 `npm run test:unit`"，AI 重新解析

### 用户此时的操作

**正常观察**（80% 场景）：
1. 看聊天窗口 — 了解叙事

3. 展开 task 详情 — 看具体操作

**主动干预**（20% 场景）：
1. 改错了文件 → 点 `[⏹ 停止当前 task]`
2. 不需要重试 → 点 `[⏭ 跳过]`
3. 想暂停 → 点 `[⏸ 暂停]`，想继续 → `[▶ 恢复]`

## 边界情况

| 边界情况 | 用户看到的 | 系统行为 |
|---------|-----------|---------|
| 同时跑 2 个 workflow | 右侧面板出现 2 个运行中条目 | 每个 workflow 独立 session |
| 用户在运行中发新聊天消息 | 新消息进入聊天流 | 排入当前 turn 队列，workflow 后台继续 |
| 浏览器刷新 | 聊天窗口空，右侧有运行中任务 | 后端缓存事件，前端重连后重建 |
| 服务端重启 | 提示 "服务已恢复" | 从 events.ndjson 重建所有任务状态 |
| Workflow 运行超长 (>10min) | Progress 持续更新 | 无超时限制，可手动停止 |
| output_file 读取失败 | Result Card 显示 "结果不可读" | 降级显示 summary 文本 |

## 设计原则总结

1. **先发现，再启动** — 用户必须先知道有哪些 workflow 可用、参数格式是什么，才能正确使用
2. **双通道互补** — 聊天窗口 = 叙事（发生了什么），右侧面板 = 结构（现在什么状态）
3. **确认再执行** — 启动前展示解析后的参数，避免误解导致错误执行
4. **默认自动** — 启动后无需干预，所有阶段自动推进
5. **异常可见** — 失败/重试/停止都有明确提示
6. **随时可停** — workflow / task / agent 每个层级都可停止
7. **断线可恢复** — SSE 断开 ≠ workflow 停止，重连可恢复视图
8. **历史可追溯** — 每次运行的 args、events、outputs 全部保留
